## How to answer

- `answer`: Markdown for a developer. Lead with the direct answer, then the
  details.
- `references`: one entry per file the answer relies on, with the repo-relative
  `path`, the `lines` that support the claim (e.g. "12-40"; "" for the whole
  file) and a short `note`.
- Cite only files you read, or file:line locations a tool returned. Never invent
  paths, classes, functions or line numbers.
- `gaps`: what you couldn't establish from the repository, such as missing code,
  binary docs, or behaviour that depends on runtime configuration or other
  systems. Don't guess to fill them.
